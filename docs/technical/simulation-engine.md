# Ядро симуляции — техническая спецификация T01

Контракт уточняет SD-11 и TD-007–TD-014 утверждёнными решениями TD-015–TD-017 и правилом R-04. Критерии ниже описывают будущие проверки T01. [Реестр решений](../decisions.md) · [TDD v0.2](TDD.md) · [Backlog](../backlog.md)

## Логическое время — TD-009

- Доменный курсор и временные отметки ядра используют `long` в миллисекундах. Шкала едина и монотонна. Все прибавления, разности и преобразования времени проверяются на переполнение. Отрицательное прошедшее время не откатывает курсор.
- `SimulationClock`, `WorldClock` и `CircadianClock` вычисляются из этой шкалы. Визуальные сутки составляют 120 реальных минут, биологические — 24 реальных часа. Кадровая частота и часовой пояс не меняют шкалу симуляции. [Биологический ритм](../design/circadian-rhythm.md)
- Источники времени внедряются через интерфейсы. Application и Infrastructure преобразуют внешние измерения в логическую цель. Domain получает шкалу и не читает системное UTC, Unity Time или платформенные часы напрямую. Автоматические тесты используют fake clock. Выбор платформенных реализаций и политика сверки недостоверного времени относятся к T03. [Целостность времени](time-integrity.md)

### Реализация T01.01c

- `GameState.LogicalTimeMilliseconds` хранит обработанный курсор в миллисекундах. `SimulationClock.GetTime(state)` возвращает типизированную отметку без изменения состояния. `LogicalTime` и `LogicalDuration` принимают неотрицательные `long`. Нулевые экземпляры допустимы. `LogicalTime.Add(duration)`, `LogicalDuration.Add(other)` и `LogicalDuration.FromHours(hours)` проверяют переполнение.
- `SimulationClock.TryGetElapsed(current, target, out elapsed)` возвращает проверенную разность. Для той же отметки это успешный нулевой интервал. Для обратной цели результат `false`, выходная длительность нулевая и интервал к обработке не допускается. Превышение диапазона при сложении или преобразовании вызывает `OverflowException`. Допустимая длительность ограничена только представимостью в `long`.
- `WorldClock(timeDefinition, cycleOrigin).Project(time)` использует визуальный период, `CircadianClock(timeDefinition, cycleOrigin).Project(time)` — биологический. Общая `CyclePhase` содержит `CycleIndex` и `ElapsedInCycleMilliseconds`. Для периода `P` и опоры `O` индекс равен `floor((time − O) / P)`, фаза — неотрицательному остатку по `P`. Опора задаёт логическую отметку начала цикла 0. До опоры индекс отрицательный, на границе фаза 0. Опоры задаются явно отдельно для каждой проекции, хранятся как миллисекунды, и при одинаковых входах расчёт воспроизводится.
- `ILogicalTimeSource.GetLogicalTime()` находится в Application и возвращает цель. В EditMode `FakeClock` поддерживает `GetLogicalTime()`, `Set(target)` и `Advance(duration)`. `Set` позволяет воспроизводить повторные и обратные показания. Обработка событий и атомарное продвижение курсора относятся к T01.02c. Паритет разбиения `AdvanceTo` проверяется вместе с ядром.

## Каноническая fixed-point арифметика — TD-010 и TD-015

Числа из [баланса v0.1](../design/balance-v0.1.md) поступают из конфигураций TD-008. Единицы времени и масштабы fixed-point являются техническими инвариантами формата.

| Данные | Представление |
|---|---|
| Логическое время | `long`, миллисекунды |
| `Value` | Целые тысячные единицы характеристики, шаг `0,001` |
| `Rate` | Знаковые целые тысячные за реальный час после применения модификаторов |
| Коэффициенты | Fixed-point с шагом `0,000001`. Коэффициент `1,25` представлен как `1 250 000` |
| `Remainder` | Целое число от `0` до `3 599 999` |
| `Denominator` | `3 600 000` миллисекунд в реальном часе |

| Игровое значение | Внутреннее значение |
|---:|---:|
| 0 | 0 |
| 0,125 | 125 |
| 25,5 | 25 500 |
| 75,123 | 75 123 |
| 100 | 100 000 |

Точное значение представлено числителем `ExactValue = Value * Denominator + Remainder`. На сегменте с постоянной скоростью выполнить три шага.

1. Вычислить `N = Value * Denominator + Remainder + Rate * ElapsedMilliseconds`.
2. Ограничить полный числитель пределами шкалы, выраженными в тех же единицах. Пороги также сравнивать по полному числителю, включая остаток.
3. Разложить ограниченный числитель на целое `Value` и канонический неотрицательный `Remainder`, меньший знаменателя.

Остаток сохраняется между вызовами, при смене скорости, в снимке и в Forecast. При насыщении отбрасывается накопление за пределами шкалы. После смены направления от границы нет скрытого долга или избытка. Одинаковые условия и события дают одинаковое состояние при произвольном разбиении.

Модификаторы применяются к базовой скорости. Итоговую скорость округляют один раз после применения соответствующих коэффициентов и ограничений, до ближайшего целого, при равенстве — от нуля. Промежуточное округление не должно менять этот результат. Проверять переполнение всех промежуточных операций. При необходимости использовать большую разрядность или математически эквивалентный безопасный расчёт. В авторитетной арифметике потребностей запрещены `float` и `double`. Преобразование для UI относится к Presentation. [Стандарты кода](coding-standards.md)

### Реализация T01.02a — принята пользователем

Приняты `BigInteger` для точной промежуточной арифметики, неизменяемые снимки `NeedsState`, явная активация модификаторов, однократное округление итоговой скорости и математический контракт пересечений числовых порогов. Закрыты CR-03, CR-05 и математическая часть CR-04. Математический паритет интегратора подтверждён. Unity скомпилировала проект, EditMode — 276 Passed, 0 Failed, 0 Skipped. Console и Production Validation — 0 ошибок, 0 предупреждений. [Рекомендации CR-13–CR-16](../backlog.md#рекомендации-code-review-t0102a)

- `NeedIntegrator.Integrate(current, rate, duration, definition)` проверяет точное исходное значение и аналитически вычисляет `N = current.ExactNumerator + rate.MilliUnitsPerHour × duration.Milliseconds` за один сегмент постоянной скорости. `System.Numerics.BigInteger` используется до насыщения. Внутри диапазона результат переводится в `long` и раскладывается через `NeedValue.FromExactNumerator`. Насыщение возвращает точную границу definition, включая её остаток. При смене скорости следующий сегмент использует точный числитель предыдущего результата. Накопление за границей отбрасывается.
- `NeedRateCalculator.Calculate(configuration, activeModifierIds)` проверяет все переданные ID до вычисления. Каталог сам по себе не активирует множители. Неизвестный или повторный ID отклоняется, ID сравниваются ordinal. Множители применяются только к целевой потребности. Точный числитель — произведение базовой скорости и коэффициентов в миллионных. Знаменатель — `1 000 000^n`. Итог округляется один раз до ближайшего целого с половинами от нуля. Если итоговая скорость выходит за диапазон `long`, расчёт выбрасывает `OverflowException`.
- `EffectiveNeedRates` содержит полную неизменяемую таблицу восьми скоростей. `NeedsIntegrator.Integrate(current, definition, rates, duration)` обрабатывает потребности в порядке `NeedId` и возвращает новый валидированный `NeedsState` через `Restore`. Исходный снимок и игровой курсор сохраняются, промежуточный результат не публикуется. CR-03 покрыт тестами инкапсуляции и обработки ошибок.
- Для текущего положения относительно порога используется `NeedValue.CompareTo`. `NeedThresholdCalculator.FindCrossings(current, rate, duration, definition)` отдельно возвращает все будущие достижения в интервале `(0, duration]`. Запись содержит потребность, точный порог, направление и относительную миллисекунду `ceil(расстояние / модуль скорости)`. Разность и модуль вычисляются в `BigInteger`, включается правая граница, сохраняются совпавшие достижения. Для абсолютной отметки ядро передаёт представимый интервал и прибавляет результат через проверяемый `LogicalTime.Add`. Порог, уже совпадающий с исходным значением, не порождает нового достижения. Технический порядок идёт по времени и по направлению движения при совпадении. Игровые последствия и EventPriority относятся к своим этапам. Это математическая часть CR-04.
- CR-05 покрыт проверками насыщения и точности при промежуточных результатах за диапазоном `long`. `BigInteger` может выделять память при больших числах и наборах множителей. Объём вычислений интегратора постоянной скорости не зависит от количества прошедших миллисекунд. Паритет разбиения на этом этапе относится к интегратору и к одинаковым границам смены скорости. Полный паритет игрового состояния online/offline/forecast остаётся задачей ядра.

## Причинная обработка событий — TD-011 и TD-016

Планировщик использует лексикографический ключ в утверждённой последовательности.

1. `Timestamp` — логическая отметка в миллисекундах.
2. `EventPriority` — меньший числовой ранг означает более высокий приоритет.
3. `SourceId` — стабильный идентификатор источника. Сравнение ordinal, независимо от культуры ОС.
4. `EventSequence` — сохраняемый монотонный счётчик для окончательного разрешения совпадений.

Порядок перечисления `Dictionary`, `HashSet` или другой коллекции не определяет выбор или регистрацию событий. Несколько дочерних событий регистрируются в детерминированном порядке. Снимок сохраняет очередь и счётчик. После обработки каждого события поместить новые события текущей отметки в общую очередь и снова выбрать минимальный ключ среди готовых. Причина выполняется до следствия. Уже обработанные события не переигрываются. Если в очереди A (приоритет `10`) и B (`20`), а A создаёт C (`5`) на той же отметке, порядок — **A → C → B**.

Корректная конечная цепочка обрабатывается до стабилизации. При цикле, превышении лимита или некорректной цепочке вернуть диагностическую ошибку ядра. Частично обработанную отметку нельзя сохранять или публиковать как успешную. Ошибочное событие не пропускается автоматически. Повтор использует согласованный checkpoint состояния, очереди, `EventSequence` и RNG, сохраняя однократность уже зафиксированных эффектов. Утверждённый первоначальный максимум событий одной отметки — `MaxEventsPerTimestamp = 256`. Значение настраивается через `SimulationConfigSO`. Его достаточность проверяется на T01.02c. Лимит защищает обработку отметки, полный офлайн-интервал сохраняется. После терминальной смерти последующие жизненные события питомца прекращаются, допустимые события мира продолжаются.

## Границы AdvanceTo — TD-012

Основной интервал продвижения — `(currentTime, targetTime]`. Входное состояние уже стабилизировано на `currentTime`. Инициализация и команды доводят события текущего момента до стабильного состояния. Так события левой границы учитываются без потерь и повторов.

| Сценарий | Поведение |
|---|---|
| `targetTime > currentTime` | Продвинуть симуляцию через полный интервал. Интегрировать между логическими границами. |
| `targetTime = currentTime` при стабильном входе | Сохранить состояние, очередь и RNG без повторных эффектов. |
| `targetTime < currentTime` | Курсор и состояние не откатываются. |
| Событие ровно в `targetTime` | Обработать в текущем вызове. |
| Несколько событий на одной отметке | Выбирать по TD-011. При порождении новых событий довести отметку до стабилизации. |
| Команда игрока | Сначала продвинуть симуляцию до времени команды, затем обработать допустимую команду и созданные ею события текущего момента. |
| Смерть внутри интервала | Прекратить жизненные процессы ровно в момент смерти. Допустимые события мира продолжаются без автоматического яйца. |

**R-04 — отказ игровой команды.** До валидации команды ядро доводит симуляцию до её логического времени. Если команда отклонена, уже рассчитанное время и закономерные события до команды сохраняются, включая их изменения состояния и расход RNG. Сама команда не изменяет состояние, не расходует ресурсы, не начисляет награду и не обращается к RNG для отклонённого действия. Если продвижение завершилось диагностической ошибкой ядра, к команде не переходят, применяется контракт TD-016.

Пакетная обработка допустима при сохранении времени, точности, порядка и RNG. GD-003 требует учёта всего фактически прошедшего интервала без защитного окна или искусственного лимита отсутствия.

### Реализация T01.02c — принята пользователем

- `SimulationEngine.Initialize(time, pet, worldSeed, initialEvents)` стабилизирует левую границу. После успеха `Initialized` содержит согласованный `State`. При сбое `InitializationFailed` содержит структурированную диагностику, `State` и `Reached` равны `null`, след пуст, транзакции не зафиксированы. Повторный `Initialize` использует исходную отметку, питомца, seed и начальные события. После восстановления успешного снимка левую границу повторно не обрабатывают.
- `AdvanceTo(state, targetTime)` проверяет состояние по текущим definitions, реестру событий, активным модификаторам и сохранённому бюджету до сравнения отметок. При корректном входе равная и обратная цели дают `NoChange` и `BackwardTarget`, а будущая обрабатывает `(currentTime, targetTime]`. Некорректный вход даёт `Fault` на отметке входного курсора с неизменённым входным снимком и пустым следом. Валидация не создаёт транзакцию, не расходует RNG и не назначает `EventSequence`.
- Исходный снимок нового мира создаётся через `GameState(logicalTimeMilliseconds, pet, worldSeed)`. Если у мира есть начальные события, готовый снимок публикует успешный `Initialize`. `GameState.Restore` принимает курсор, питомца, неизменяемые снимки RNG и очереди, активные ID модификаторов и число уже обработанных событий текущего курсора. На восстановлении используется сохранённое состояние всех шести потоков без повторного seeding. Стабильный снимок допускает только будущие события и проверяет принадлежность событий жизни живому питомцу.
- `EventQueueSnapshot` копирует полные неизменяемые события в каноническом порядке и сохраняет `NextSequence`. Событие содержит абсолютную отметку, числовой приоритет, устойчивые ID источника и типа, область, привязку к питомцу для жизненных событий и данные payload. Обработчики хранятся в отдельном реестре. Рабочая очередь использует `SortedSet` и ключ `Timestamp → Priority → SourceId (ordinal) → Sequence`. После каждого обработчика снова выбирается минимум. Свойства TD-016 подтверждает след `A → C → B`.
- `EventSequence` — неотрицательный `long` с началом в 0. Он даёт однозначный номер регистрации при восстановлении, отменах и переходах между отметками. Номер присваивается в объявленном порядке регистрации. `long.MaxValue` обозначает исчерпанный счётчик. Проверяемое увеличение выявляет переполнение до добавления события.
- На каждом шаге граница — минимум из цели, ближайшего события и ближайшего математического порога. `NeedRateCalculator` учитывает активные модификаторы, `NeedsIntegrator` сохраняет все fixed-point остатки. Ядро до интегрирования собирает все совпавшие достижения восьми потребностей в порядке `NeedId` и направления прохождения порогов. В очередь попадает только обрабатываемая отметка. После стабилизации скорость и будущие пороги пересчитываются. Техническое событие `need.threshold` несёт точное значение, направление и абсолютное время. Его приоритет 0 относится к текущему срезу.
- Отрезок интегрирования и стабилизация его конечной отметки образуют одну транзакцию. Контекст восстанавливает рабочие очередь и RNG. Побочные изменения ограничены контекстом домена. После успеха ядро публикует курсор, питомца с остатками, модификаторы, очередь, `NextSequence`, RNG и след. При ошибке продвижения существующего мира `Fault` сохраняет последний согласованный снимок и след предыдущих отметок. Необработанное событие остаётся доступным для точного повтора.
- `SimulationResult` содержит исходную и целевую отметки, необязательную достигнутую отметку `LogicalTime? Reached`, снимок при его наличии, след успешных событий, счётчики транзакций и математических границ, статус и причину отказа либо структурированную диагностику. Диагностика включает код, отметку, проблемное событие при наличии, объяснение и лимит при его превышении. Фатальные ошибки среды и отмена выполнения распространяются вызывающему коду.
- Лимит `Simulation.MaxEventsPerTimestamp` относится ко всем причинно обработанным событиям одной отметки, включая инициализацию и последовательные команды. Счётчик хранится в снимке и сбрасывается при переходе к другой отметке. Тело команды само по себе не является событием. Это техническое правило текущего среза. Production допускает ровно 256 событий и откатывает отметку при попытке обработать 257-е. Две отметки по 256 событий пройдены полностью.
- `PetState.TerminatedAt` фиксирует явный терминальный переход с сохранением `PetId`. Оставшиеся готовые и все будущие события жизни этого питомца отменяются без эффектов и расхода RNG. Потребности замораживаются, мир продолжает обработку до цели. Успешные события перед переходом сохраняются. Нулевое здоровье в этом срезе само по себе не вызывает переход. Автоматического яйца нет.
- `ExecuteCommand(state, time, command)` реализует R-04. `ISimulationCommand.Validate` получает неизменяемое состояние после естественного продвижения. Отказ сохраняет его и естественный след без эффектов команды. После допуска `Apply` и его причинные события проходят в отдельной транзакции. ## Детерминированные потоки PCG32 v1 — TD-013 и TD-017

Утверждён PCG32 с независимыми сериализуемыми потоками `Birth`, `Behaviour`, `Illness`, `Evolution`, `Lifecycle`, `Digestion`. Сохраняются внутреннее состояние и идентификатор последовательности каждого потока, версия алгоритма хранится отдельно. Инициализация стабильна, добавление потока не меняет существующие последовательности. В T01 реализуется общий механизм. Игровые системы подключаются по мере реализации.

- Для авторитетной случайности в Domain запрещены `UnityEngine.Random` и `System.Random`. Визуальная случайность не расходует доменные потоки.
- Потребление RNG привязано к определённым логическим событиям и сохраняемому прогрессу. Разбиение интервала, перезапуск и загрузка не порождают лишних случайных значений. Forecast использует копию всех потоков.
- Для ограниченных целочисленных диапазонов нужна равномерная выборка без систематического смещения. Проверяются эталонные последовательности, независимость и продолжение после восстановления состояния.

`RngAlgorithmVersion = 1` закрепляет референсный PCG XSH RR 64/32 с выбираемым потоком и беззнаковой арифметикой по модулю `2^64`. Выход длиной 32 бита строится из состояния до перехода, как в `pcg32_random_r`. Константы алгоритма являются техническими инвариантами. Для каждого мира сохраняется явный `WorldSeed` типа `uint64`, который используется как `initstate`. `initseq` берётся из стабильного реестра. Новые потоки получают новые 63-битные селекторы без перестановки старых.

| Поток | `SequenceId` |
|---|---:|
| Birth | 1 |
| Behaviour | 2 |
| Illness | 3 |
| Evolution | 4 |
| Lifecycle | 5 |
| Digestion | 6 |

Двухшаговая инициализация следует `pcg32_srandom_r`. Установить состояние в ноль и нечётный инкремент `2 × initseq + 1`, выполнить переход без выдачи значения, прибавить `initstate` по модулю `2^64` и выполнить второй переход без выдачи. Снимок содержит отдельно `RngAlgorithmVersion` и для каждого потока `StreamId`, `SequenceId`, `State`. При восстановлении вычислить инкремент из селектора и установить сохранённый `State` без повторной инициализации. Формат 64-битных значений в файле определяется в T03. Точное шестнадцатеричное представление рекомендуется.

Для диапазона `[0, bound)` при `1 ≤ bound < 2^32` применяется rejection sampling. Отбросить результаты `r < 2^32 mod bound` и вернуть `r mod bound`. Некорректный `bound` проверяется до вызова RNG. Утверждённые эталоны версии 1 приведены ниже. [Референсная реализация PCG](https://github.com/imneme/pcg-c-basic) · [Опубликованный эталон](https://www.pcg-random.org/using-pcg-c-basic.html)

| Вектор | Вход и ожидаемый результат |
|---|---|
| Референс | `initstate=42`, `initseq=54` → `a15c02b7`, `7b47f409`, `ba1d3330`, `83d2f293`, `bfa4784b`, `cbed606e`. |
| Продолжение из снимка | Селектор `54` и состояние `f7079824c154bf23` после третьего значения → `83d2f293`, `bfa4784b`, `cbed606e`. |
| Потоки проекта | `worldSeed=42`, `Birth` (`initseq=1`) → `4df1ccf9`, `e5838752`. `Behaviour` (`initseq=2`) → `ff85ecc9`, `4de4d2f6`. Чередование или добавление третьего потока не меняет эти пары. |
| Ограниченный диапазон | `bound=10`, фиксированные сырые значения `0`, `5`, `6` → отбросить `0` и `5`, вернуть `6` после трёх чтений. |

## Forecast, терминальный статус и инварианты

- Online, offline и Forecast вызывают одно ядро. Forecast получает независимые `GameState`, прогресс событий, дробные остатки и снимки RNG. Он возвращает прогноз и не изменяет рабочее состояние, ресурсы, сохранение и внешние сервисы.
- Минимальный терминальный статус T01 останавливает тестовые жизненные процессы с момента завершения. Полноценные игровые правила здоровья и смерти входят в T02. Уведомления, платформенные часы и персистентный формат добавляются по своим этапам.
- Равные исходные состояние, definitions, команды, события и RNG дают одинаковые итоговые состояние, курсор, остатки, логический след событий и RNG. Доступность, модификаторы и однократность эффектов принадлежат Domain. [Симуляция питомца](../design/pet-simulation.md)
- Конфигурации проверяются и преобразуются в immutable definitions по TD-008 и TD-014. T01 ограничен шестью утверждёнными типами и минимальными тестовыми правилами. [Конфигурации T01](configuration-system.md)

### Реализация T01.03a — принята пользователем

`IdlePet.Domain.State.GameStateCloner.Clone(source)` создаёт самостоятельный `GameState` через `Restore`. Сохраняются курсор, наличие и ID питомца, терминальная отметка, все восемь fixed-point значений с остатками, снимок всех шести потоков PCG32 v1, очередь с полными payload и номерами, `NextSequence`, активные модификаторы и `ProcessedEventsAtCursor`. Новый объект владеет отдельной защищённой коллекцией ID модификаторов. Доказуемо неизменяемые `PetState`, `NeedsState`, снимки RNG и очереди, записи событий, значения и строки могут использоваться совместно. Их конструкторы принимают данные снимка, а публичные коллекции доступны только для чтения. `GameConfiguration` и definitions также неизменяемы. Каждая транзакция создаёт рабочие RNG, планировщик, набор модификаторов и контекст из своего checkpoint.

`IdlePet.Application.Forecast.ForecastService(SimulationEngine)` принимает тот же экземпляр ядра, что и обычная симуляция. `Forecast(source, targetTime)` проверяет пригодность реестра, клонирует источник и передаёт копию в существующий `AdvanceTo`. `ForecastFor(source, duration)` использует проверяемое сложение логического времени. Отсутствующий источник даёт `ArgumentNullException`, непредставимая цель по длительности даёт `OverflowException`. Forecast возвращает неизменяемый `ForecastResult` со статусом, отметками, отдельной ветвью, следом, диагностикой и счётчиками. Он вычисляет только естественные события. Прогнозный след остаётся результатом вычисления, исходный мир не меняется и внешние действия не выполняются.

- При валидной равной или обратной цели возвращаются `NoChange` или `BackwardTarget` и независимый снимок. При ошибке входа `Fault` отмечается через `SimulationDiagnostic.IsInputStateFailure`. Возвращённая ветвь в этом случае не прошла проверку конфигурацией. При сбое обработки `Fault` содержит последний согласованный прогнозный checkpoint и только зафиксированный след. Ошибка инициализации сохраняет контракт CR-21, где `State` и `Reached` отсутствуют.
- CR-24. Публичный `SimulationEngine(GameConfiguration)` использует правила доверенного Domain. В текущем Production-срезе ядро регистрирует собственные события математических порогов. Внутренний `SimulationRuleSet` принимает только известные Domain операции `SimulationRuleEffect` с неизменяемыми данными и выполняет их через `SimulationEventContext`. ID сравниваются ordinal, дубликаты и зарезервированный ID порога отклоняются, набор операций копируется при регистрации. В обоих режимах используется один реестр ядра.
- Прежняя регистрация произвольных `Action` доступна только через `SimulationEngine.CreateForTests` существующей EditMode-сборке. Такой реестр отклоняется со статусом и диагностикой `UnsupportedRuleSet` до копирования и выполнения, даже если цель раньше первого события. `State` и `Reached` при отказе отсутствуют. Доверие к контролируемым операциям опирается на закрытую регистрацию, ограниченный контекст и проверку кода. Универсальная проверка чистоты C# и песочница в этот срез не входят.
- Прогноз терминального перехода сохраняет питомца и точную отметку, отменяет жизненные события без дополнительного расхода RNG и продолжает мировые события. При последующем сбое той же отметки терминальный переход откатывается вместе с рабочей очередью. Питомец исходного мира сохраняет прежнее состояние.

| Произвольные разбиения интервала | Повторить с детерминированными нерегулярными разбиениями, включая доли логических сегментов и точки событий. Итоги совпадают. |
| Дробные остатки, пороги и округление | Снимок сохраняет остаток при разбиении и смене скорости. Порог сравнивается по полному числителю. Итоговая скорость после модификаторов округляется один раз, проверяются половины обоих знаков. |
| Минимум и максимум | Оба предела соблюдаются при движении наружу. |
| Смена направления расхода или восстановления | На обоих пределах новый шаг внутрь начинает расчёт от границы. Скрытой задержки, выброса или долга нет. |
| Переполнение времени и промежуточных чисел | Непредставимая операция диагностируется без wraparound и некорректного игрового результата. |
| Событие ровно на правой границе | Его эффект виден после текущего вызова и применён один раз. |
| Повтор с той же целью | После стабилизации не меняются значения, остаток, очередь и RNG. |
| Попытка продвижения назад | Состояние и курсор сохраняются. |
| Инициализация и команда на левой границе | Начальные события учитываются один раз. До команды обработана её отметка, созданные ею события обрабатываются до стабилизации. |
| Отклонённая команда | Сравнить с продвижением к тому же времени без команды. Состояние, события, ресурсы, награды и RNG совпадают с этим контрольным прогоном. Диагностическая ошибка ядра проверяется отдельно. |
| Несколько событий в одной временной точке | При равенстве предыдущих ключей используются следующие, вплоть до `EventSequence`. |
| Новое событие на текущей отметке | Готовая очередь обрабатывается до стабилизации. Проверить A → C → B и детерминированную регистрацию нескольких дочерних событий. |
| Перестановка коллекций и смена культуры | Разный порядок перечисления и настройки культуры дают одинаковый логический след. Снимок сохраняет следующий порядок. |
| Бесконечная цепочка без продвижения | Защита возвращает диагностическую ошибку без публикации или записи частичной отметки. Повтор из checkpoint сохраняет очередь, `EventSequence`, RNG и однократность ранее зафиксированных эффектов. |
| Воспроизводимость PCG32 | Эталонные выходы совпадают. Диапазон, ширина которого не делит `2^32`, проверяется вектором с отбрасыванием значений ниже порога. |
| Независимость RNG-потоков | Потребление и добавление другого потока не меняет существующую последовательность. |
| Восстановление RNG | Состояние и селектор дают точное продолжение. Повтор загрузки или дополнительный разрез не потребляет лишние значения. |
| Forecast | Прогноз воспроизводим, исходные `GameState`, очередь, остатки и RNG побайтно или структурно эквивалентны исходному снимку. Внешних эффектов нет. |
| Некорректные конфигурации | Валидатор диагностирует отсутствующие ссылки, выход из диапазона и дубли ID. В Release доступен только Production. |
| Независимость Domain от Unity | Доменная сборка не ссылается на UnityEngine, чистые сценарии выполняются без Unity API. |
| Минимальный терминальный сценарий | Тестовое завершение внутри интервала прекращает последующие жизненные события без повторных эффектов и автосоздания яйца. |
