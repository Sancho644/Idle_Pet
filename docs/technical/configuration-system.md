# Система конфигураций — TD-008 и TD-014

TD-008 определяет архитектуру, а TD-014 закрепляет шесть типов Authoring первого среза T01. Специализированные каталоги расширяются по мере реализации игровых механик. [Реестр решений](../decisions.md) · [TDD](TDD.md) · [Backlog](../backlog.md)

## Утверждённый объём T01

| Конфигурация | Назначение |
|---|---|
| `GameConfigSO` | Корневой каталог, связывает конфигурации и профили. Используется в композиции как данные. Глобальный mutable singleton и service locator запрещены. |
| `SimulationConfigSO` | Настраиваемые параметры симуляции первого среза, включая максимум событий одной отметки по TD-016. Число задаётся конфигурацией и проверяется валидатором. |
| `TimeConfigSO` | Настраиваемые параметры логических проекций времени. Миллисекундная единица курсора задаётся контрактом TD-009. |
| `NeedsConfigSO` | Начальные значения, скорости и пороги потребностей. |
| `ModifierConfigSO` | Настройки модификаторов и их логических каналов. |
| `BalanceProfileSO` | Выбор и привязка параметров к одному из профилей баланса. |

Сохраняются `Production`, `FastTesting` и `StressTesting`. В Release игроку доступен только `Production`. Настройки и критерии отличия профилей описаны в [балансе v0.1](../design/balance-v0.1.md).

## От авторинга до Domain

| Участок | Ответственность |
|---|---|
| `GameConfigSO` | Корневой ассет связывает специализированные конфигурации, каталоги и выбранный профиль баланса. |
| Настройки и каталоги | T01 использует только утверждённый объём выше. Конфигурации жизненного цикла, характеров, особенностей, болезней, освещения, пищи, мебели, видов и форм добавляются со своими системами. Модели, префабы, звуки, VFX, визуальные параметры и ключи пользовательского текста задаются в конфигурациях. |
| Config Mappers | Authoring проверяет данные и переводит ссылки в стабильные ID и неизменяемые чистые C# definitions. Unity-ассеты представления остаются в Authoring/Presentation. |
| DI | Composition root передаёт проверенные определения потребителям через конструкторы. Domain работает с данными без Unity API. VContainer отложен до Bootstrap по TD-003. |
| Runtime | Текущие потребности, ресурсы, действия, RNG, настройки игрока и результаты симуляции принадлежат `GameState` и сохранению. ScriptableObject во время игры остаются исходными данными. |

## No Hardcode

Все настраиваемые игровые параметры, пороги, тайминги, коэффициенты, вероятности, определения контента и ссылки на ресурсы поступают из конфигураций. Добавление экземпляров контента в рамках существующей механики выполняется через ассеты и каталоги. Пользовательские тексты и шаблоны хранятся в String Tables, ключи задаются конфигурациями. [Стартовый баланс](../design/balance-v0.1.md) · [Локализация](localization.md)

В коде допустимы алгоритмы, технические перечисления, идентификаторы протокола и инварианты вроде монотонности курсора, единиц времени, масштабов fixed-point и констант PCG32. Игровые скорости, пороги, коэффициенты и лимит событий хранятся в конфигурациях. Тестовые fixtures содержат явно маркированные тестовые данные и изолированы от Production. Для отсутствующих обязательных данных production-код выдаёт ошибку валидации. Скрытые запасные значения баланса запрещены. [Инварианты ядра](simulation-engine.md)

## ID, версии и валидация

- Стабильный ID уникален в своей области и сохраняется при переименовании и перемещении ассета. `GameState` и сохранение хранят ID и данные, пригодные к сериализации. Старые ID не переиспользуются.
- Отдельно версионируются схема сохранения, правила симуляции, баланс, контент и алгоритм RNG. При маппинге definitions сохраняют версии исходных конфигураций правил, баланса и контента. Политика миграции и обработка отсутствующих ID требуют решения до T03. [Вопросы O-20 и O-21](../open-items.md)
- Автоматически проверяются обязательные ссылки, диапазоны, совместимость особенностей, доступность поддерживаемых конфигураций, дубли ID, графы эволюции, ссылки на локализацию и доступность обязательного ухода. Валидация покрытия расширяется вместе с каждой системой.
- При авторинге ошибки должны указывать ассет и поле. После реализации валидатора критическая ошибка блокирует сборку. Релизу доступен только профиль Production. [TDD](TDD.md)

## Проверки первого среза

- Смена значения в тестовой конфигурации меняет definition и расчёт без правки Domain. Ошибочный диапазон, пропущенная ссылка или дублирующийся ID диагностируются.
- Definitions не содержат Unity-типов и не изменяются симуляцией. Разные `GameState` используют общий набор definitions без общего изменяемого состояния.
- Проверяется маппинг шести типов первого среза и выбор допустимого профиля. Критические ошибки блокируют сборку после реализации валидатора. Каталоги будущих систем, VContainer и пакет Unity Localization планируются на соответствующие этапы после согласования. [Критерии ядра](simulation-engine.md)

## Реализация T01.01b

`GameConfigSO` ссылается на один явно выбранный `BalanceProfileSO`. Профиль содержит стабильный ID, вид профиля и ссылки на Simulation, Time, Needs и Modifiers. Версии правил и контента задаются в корневом ассете, версия баланса — в профиле. В Inspector версии записываются в формате `major.minor` или `major.minor.patch`.

`GameConfigMapper.Map(root, target, assetPath)` возвращает `ConfigurationMappingResult` с неизменяемой `GameConfiguration` и диагностикой. В вызове явно передаётся `ConfigurationTarget.Release` или `ConfigurationTarget.Testing`. Критическая ошибка оставляет `Definition` пустым. Диагностика содержит код, серьёзность, ассет, поле и сообщение. Параметр `assetPath` необязателен. Editor передаёт `AssetDatabase.GetAssetPath`. Потребитель передаёт полученные definitions через конструктор, включая `GameConfiguration.Needs` для создания `NeedsState`.

В Inspector значения потребностей и скорости в единицах за реальный час записываются десятичным текстом с точкой и точностью до трёх дробных цифр. Поле коэффициента поддерживает до шести. Маппинг проверяет формат, точность и переполнение, преобразует данные в целые тысячные или миллионные и инициализирует нулевой остаток потребности. Длительности вводятся целыми минутами, часами или днями согласно названию поля и переводятся в миллисекунды с проверкой переполнения. CR-01 применяется к множителям скорости хранимых потребностей. Допустимы неотрицательные коэффициенты, включая ноль.

Корень Production находится по пути [GameConfig.asset](../../Assets/_Project/Content/Configs/Resources/IdlePet/GameConfig.asset). Путь ресурса — `IdlePet/GameConfig`. Он однозначно определяет граф из шести ассетов для Player. В текущем срезе FastTesting и StressTesting создаются в EditMode-тестах как временные объекты. Release принимает только Production. По CR-06 у всех найденных профилей, включая Production и вложенные ассеты, проверяются формат и уникальность стабильного ID и допустимость `BalanceProfileKind`. ID сравниваются через `StringComparer.Ordinal` с учётом регистра. Диагностика дубля содержит основной путь и `RelatedAssets` с остальными конфликтующими путями.

Меню **Tools → Idle Pet → Validate Game Configuration** находит единственный корень, применяет общий маппер и учитывает включённые сцены активного Build Profile или глобального списка. Предсборочный `BuildPlayerProcessor.PrepareForBuild` передаёт фактический список из `BuildPlayerOptions.scenes`. При отсутствии явного списка используется открытая активная сцена. При критической ошибке предсборочная проверка выбрасывает `BuildFailedException` с диагностикой.

По CR-07 проверяются прямые и транзитивные зависимости корня Production, runtime Resources, сцен сборки, Preloaded Assets и назначенных render pipeline assets. Тестовый профиль из этого графа блокирует сборку, в том числе при размещении в `Editor` или `Assets/Editor Default Resources`. Постоянные ассеты тестовых профилей допускаются только в Editor-only папках без входящих ссылок из графа Player. Папка `Editor Default Resources` считается специальной только непосредственно в `Assets`. Проверка графа выполняется через `AssetDatabase`. Проверка состава готовых Player по CR-08 отложена на [T05](../backlog.md#отложенные-проверки-первого-игрового-прототипа). [Правила специальных папок Unity](https://docs.unity.com/en-us/engine/6000.6/manual/get-started/project-configuration/special-folders)

Пользователь утвердил первоначальный технический лимит `MaxEventsPerTimestamp = 256` по TD-016. Лимит настраивается через `SimulationConfigSO`. Его достаточность проверяется на T01.02c. Длительность офлайн-прогресса остаётся полной. Профиль содержит пустой каталог модификаторов. Приняты версии правил, контента и баланса `0.1`.
